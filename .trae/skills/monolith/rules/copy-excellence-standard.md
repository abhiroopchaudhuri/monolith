# Rule — Copy Excellence Standard

Every user-visible string in the generated app is written by `ux-writer` with intent, not inherited from PRD or generated by developer by convenience. Copy is product, not decoration.

## The scope of "user-visible string"

- Page titles, subtitles, section headings
- Button labels, menu items, tab names
- Input labels, placeholders, helper text
- Empty-state / loading-state / error-state content
- Toast and snackbar messages
- Modal titles, descriptions, action labels
- Tooltip content
- Table column headers
- Breadcrumbs
- Navigation item labels (where the DS allows custom names)

NOT in scope:
- Fixture data that represents real domain content (patient names, strategy names, etc. — these are domain content, not UX copy).
- DS component internals (the DS owns those).

## The ux-writer pass

### When it runs

After design-principal's critique concludes (so structural/layout changes are done), before developer's full-gen completes. If design-principal revises late, ux-writer re-runs on just the changed screens.

### What it does

1. Extracts every in-scope string from the planned screens (reading `docs/build_specs.md § file-level content` + any screen stubs the developer has drafted).
2. Rewrites each string against four criteria:
   - **Clarity**: the next action is obvious.
   - **Specificity**: names the object + context, not the type.
   - **Voice**: matches `guidelines/voice.md`.
   - **Differentiation**: reinforces `differentiation-map.md` bets where applicable.
3. Records before/after per string in `<runRoot>/docs/ux-writing-pass.md` with weight (from `evidence-weighted-decisions.md`).
4. Hands the list to developer (or self-healer if developer has already run) for application.

## The five string-level tests

Every string must pass these before being written to code:

### Test 1 — Active verb for actions

Button/action labels start with a verb. "Export report" not "Report export." "Start dry run" not "Dry run."

Exceptions:
- Toggle labels (they name a state, not an action).
- Single-concept items in a menu where context is clear.

### Test 2 — Specific objects

Name the noun specifically. "Delete strategy" not "Delete." "Assign 847 patients" not "Assign."

Button labels that can't fit the full object use a fallback pattern: short label + tooltip or aria-label with full context.

### Test 3 — Next-action orientation

Labels and helper text tell the user what to do next, not what the system is. "Enter EMPI to search" not "EMPI field."

Empty states and error messages must end with a clear CTA: what the user can do from this state.

### Test 4 — No type-name exposure

Don't leak the implementation's noun types. "More options" not "Kebab menu." "Settings" not "Preferences panel." "Switch workspace" not "Organization selector."

### Test 5 — Voice consistency

Match the tone documented in `guidelines/voice.md`. If voice is "clinical and precise," avoid cutesy exclamations and metaphors. If voice is "warm and reassuring," avoid clipped imperatives. ux-writer uses voice.md as the constitution for every choice.

## Domain-specific calibration

Different domains tolerate different levels of warmth, formality, and density:

| Domain | Register | Example |
|---|---|---|
| Clinical / healthcare | Precise, restrained, factual | "Dry Run — No assignments will be changed" |
| Finance / accounting | Transactional, specific, auditable | "Post journal entry to Q4 ledger" |
| Consumer creative | Warm, playful, direct | "Drop your files here" |
| Developer tools | Dense, terse, technical | "npm install — 412 packages" |
| B2B enterprise | Professional, confident, business-outcome | "Deploy to production" |

ux-writer reads the domain from triage's classification and calibrates accordingly.

## Emoji and punctuation

- Emoji in user-facing copy is **off by default**. Enabled only if `guidelines/brand.md` explicitly sanctions it.
- Exclamation marks are **off by default**. They read as desperate in most B2B/clinical domains. Enabled only if voice.md sanctions.
- Ellipses are used for in-progress actions ("Saving…") but not for vague promises ("coming soon…" — use "coming soon" instead).
- Em-dashes are fine. Semicolons are fine. En-dashes for number ranges.

## Translation-readiness

Every string is written to be translatable:
- No sentence-in-sentence assembly ("You have {n} {items}" — pick one: "You have 5 strategies" or "Strategies: 5").
- Avoid puns and idioms unless voice.md explicitly allows them.
- No string concatenation across languages in code (one string = one translatable unit).

## Handling the PRD's copy

The PRD often includes draft copy. ux-writer treats PRD copy as:
- **Informative** — the PRD's phrasing reveals how the PM thinks about the concept.
- **Provisional** — rewritable unless the PRD explicitly names a string as "final, voice-defining" (e.g., the product's official feature name).

When PRD copy survives the pass unchanged, it's still recorded in ux-writing-pass.md with weight `[grounded — PRD verbatim]`.

## Integration with differentiation

For each screen that serves a differentiator (per differentiation-map.md), ux-writer checks that at least one string reinforces the bet:
- Transparency differentiator → copy names what's visible that wasn't before.
- Speed differentiator → copy counts saved time or steps.
- Trust differentiator → copy names consequences and reversibility.

If no string reinforces the differentiator, the screen's copy is not done.

## Anti-patterns (fail immediately)

- Labels that are just the schema field name ("StartDate" not "Start date").
- "Please" in action labels ("Please click to save").
- "Are you sure?" without the consequence.
- "Error" as the whole error message.
- "Click here" as link text.
- "Loading…" when a specific loading message is available.
- Generic empty states: "No results."
- "For more information, contact support" with no path.

## Success gate

- `ux-writing-pass.md` exists with every in-scope string rewritten (or preserved with reasoning).
- Every differentiator screen has at least one differentiator-reinforcing string.
- No PRD-verbatim copy that fails tests 1–5 is left in the code.
- design-principal has reviewed the ux-writing-pass for tonal consistency and approved.
