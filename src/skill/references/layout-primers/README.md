# Layout primers

Canonical layout shapes the ux-architect and lead-designer can reference.

## Primers

*(seed content; extend as patterns emerge)*

### Dashboard
- Purpose: at-a-glance status with drill-downs.
- Typical sections: top bar → summary-metric strip → primary work region (list/table/charts) → secondary context pane.
- Density: usually `comfortable`; switch to `compact` for power users.
- A11y: landmarks — banner/nav/main/aside. Focus: top-bar menu first.

### Detail page
- Purpose: one entity, all facets.
- Typical sections: breadcrumb → title + actions → tabs OR section stack → metadata sidebar.
- Density: `comfortable`.

### List / table
- Purpose: browse + find.
- Typical sections: filters → bulk actions → table → pagination.
- Density: `compact` often warranted.

### Form
- Purpose: capture + validate input.
- Typical sections: title + intent → grouped fields → helper + error → submit bar.
- Density: `comfortable`.

### Wizard
- Purpose: multi-step guided task.
- Typical sections: progress indicator → step body → back/next/skip controls.

### Empty state
- Purpose: guide users before they have data.
- Includes: icon/illustration, headline, one-sentence help, primary action.

### Error state
- Purpose: explain + recover.
- Includes: calm headline, one-sentence cause, primary recovery action, secondary "contact support."

## How these are used

The ux-architect references primers when building IA; the lead-designer references them when mapping sections to DS components. Primers are not rules — they are starting points. Any deviation is fine if justified in design_decisions.md.

## Adding a primer

New primers live as top-level sections here (not separate files) unless they grow long. Keep each ≤1 screen's worth of text.
